 GPT-4.1 in UK South Only Designing a regulator-ready Azure OpenAI platform for UKLifeLabs with PTU, private networking, and dual API gateways Executive summary UKLifeLabs requires GPT-4.1 inference to occur exclusively within the UK South Azure region. To meet this requirement in a defensible way, UKLifeLabs uses an Azure geography deployment in UK South, reserves capacity using Provisioned Throughput Units (PTU), blocks public access using private endpoints, and enforces access and throttling through two API Management gateways (internal and external). The moment the requirement became real Everything looked straightforward until a single question landed in a meeting: “If we do not reserve capacity, can inference be processed outside UK South?” This is where many teams get misled by a false binary: PTU versus pay-as-you-go. The real control knob is deployment processing scope: Global, Data Zone, or Azure geography. If Global or Data Zone is used, inference can be processed outside a single region. For UKLifeLabs, that is not acceptable. The requirement Model: GPT-4.1 Region: UK South only Rule: Prompts, inference processing, and responses must not be processed outside UK South. No global fallback. The decision drivers UK South-only inference requires avoiding Global and Data Zone deployment types. GPT-4.1 is capacity-constrained. Without reserved capacity, you risk being pushed to Global processing patterns. PTU is not a regulatory checkbox. It is the practical mechanism to reserve GPU capacity in-region for GPT-4.1. Two gateways are required because internal and external users have different trust levels, controls, and throttling needs. The architecture UKLifeLabs uses a single AI Hub subscription in UK South that hosts the Azure OpenAI resource and PTU-backed deployments. All workloads, whether internal or external, reach the model only through API Management. Direct access is blocked. Regulator-ready Q&amp;A Q: How do you ensure GPT-4.1 inference stays in UK South? A: We use an Azure geography deployment in UK South and reserve capacity using PTU. Global and Data Zone deployments are explicitly excluded. Connectivity is private and access is only via governed API gateways. Q: Why PTU? A: PTU is not a regulation requirement. For GPT-4.1 with a strict UK South-only requirement, PTU is the practical mechanism that reserves in-region GPU capacity and reduces the risk of global processing patterns when capacity is constrained. Q: Can developers bypass the gateway and call the model directly? A: No. Public access is disabled and network controls allow only the API gateways to reach the private endpoint. Q: How is production protected from dev/test and external spikes? A: Separate deployments plus APIM products and throttles ensure dev/test and external traffic cannot consume prod allocation. Q: Where are logs stored? A: Logs are centralized in UK-hosted monitoring, with request correlation IDs and identity metadata for auditability. Common misconceptions PTU alone guarantees UK South only. False. You must also avoid Global and Data Zone deployment scopes. Pay-as-you-go always stays in-region. False. Global processing options can route inference outside a region. APIM is optional. False for regulated environments. Without it, you lose consistent identity, throttling, and audit controls.
